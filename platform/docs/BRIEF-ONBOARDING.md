# Бриф Google Forms → проект и подготовка запуска

## Согласованный результат

Источник: Google spreadsheet `1SvEG8VNqmGhhND9UGyKXBbKczjTA__nG8Lla7EPtVyA`,
лист `Ответы на форму (1)`, gid `269775685`, timezone `Asia/Dubai`.
Копия листа и `old` не обрабатываются. При первоначальной проверке найдено
117 заполненных ответов. Они не импортируются автоматически.

Пользователь разрешил создавать папку в Google Drive и полную карточку проекта
в платформе для каждого нового брифа. При открытии нового проекта в мастер-кабинете
появляется сохраняемое окно подготовки для медиабайера: проверка брифа, назначение
ответственного и доступов, материалы, план/дедлайны, кабинет, события, CAPI, CRM,
креативы, бюджет/KPI и проверка запуска.

Проект создаётся приватным draft (`project_type: unconfigured`), без придуманных
валюты/часового пояса, расходов, интеграций, приглашений или автоматического запуска
рекламы. Это карточка подготовки внутри `/master`, не опубликованный клиентский
отчёт с готовыми рекламными данными. В форме нет отдельного названия компании:
если соответствующего вопроса нет, временное название берётся из указанного URL
и отмечается для уточнения. Уточнения карточки не переписывают исходный бриф.

## Что реализовано

- `migrations/0037_project_onboarding.sql`: изолированные brief_sources и
  project_onboarding; полный исходный бриф, профиль, чек-лист, версия и папка.
- `onboarding/model.js`: сопоставление заголовков, полный исходник, стартовые задачи,
  проверка статусов, дат, уточнений и обязательных комментариев проверки.
- `onboarding/api.js`: отдельный scoped intake и защищённые master GET/PATCH.
- `onboarding/ui.js` / `ui.css`: окно карточки/запуска, полный бриф, уточнения,
  дедлайны, ответственные, прогресс, защита несохранённых изменений и настройка Google.
- `onboarding/apps-script.js`: готовый код bound Apps Script без секрета в исходнике.
- `scripts/configure-brief-intake.py`: подготовка схемы, единственного источника
  и зашифрованного Worker secret `BRIEF_INTAKE_TOKEN`; существующие строки не читает.

Google parent был создан как `TOYS — Проекты`, ID
`1OrCr9Zjqz3we4cwxR6gS0Jh5lXOks_W_`. Если установщик использует другой Google-аккаунт
и не имеет доступа, setup создаёт корневую папку под его аккаунтом и регистрирует
её до первого проекта, не расширяя доступ к исходной папке. После первого проекта
нельзя незаметно поменять parent: endpoint требует отдельной проверки.
Назначение сотрудника в платформе не выдаёт ему доступ Drive: это отдельный
пункт чек-листа, которым управляет владелец папки.

## Как включить

В рабочем мастер-кабинете на «Главной», при выборе «Все проекты», администратору
доступна кнопка **«Подключить брифы»**. В окне есть готовый код, scoped ключ,
ссылка на таблицу и индикатор проверки из Google.

1. Открыть исходную таблицу под Google-аккаунтом, который может её редактировать.
2. Расширения → Apps Script: вставить код из платформы и сохранить.
3. Выбрать и выполнить `setupTOYSBriefIntake`, разрешить действия Google.
4. В появившееся окно вставить scoped ключ из кнопки «Скопировать ключ» в платформе.

Ключ не писать в ячейки, репозиторий или сообщения. Это ключ приёма брифов, не
учётные данные рекламных кабинетов и не административный доступ к финансам.

Setup проверяет авторизацию, сохраняет baseline после последнего текущего ответа
и устанавливает onFormSubmit и повтор каждые 5 минут. После установки чат не нужен.
Немедленный путь запускается событием отправки формы; пять минут — повтор после
ошибок/пропущенного события, не почасовой мониторинг ChatGPT. Реальное время
доставки и квоты зависят от Google Apps Script; не обещать строгую задержку 0 секунд.

Инструментов установки Apps Script в этом чате нет. Публикация Worker и сохранённый
источник не означают, что Google-триггер установлен. До пользовательского setup
не заявлять о работающем автоматическом приёме. `last_checked_at` подтверждает
проверку из Google, `last_received_at` и реальные project_onboarding — поступления.
Сам факт проверки ещё не доказывает установку обоих триггеров.

## Идентичность, повторы, доступ

Ключ ответа строится из фиксированного источника и оригинального timestamp
формы в UTC. Row index не является идентичностью: сортировка не создаёт второй
проект при повторной доставке той же записи. Разные ответы с одинаковым точным
timestamp вызывают конфликт, а не перетирают карточку. Два отдельных отправления
с разным временем создают два draft; клиенты не сливаются по домену или телефону.

Для активного листа использовать добавление ответов Forms, без удаления и сортировки:
Apps Script читает новые строки по durable cursor. Перестановка/удаление строк может
изменить очередь; для аналитики использовать копию листа. Текущий блок сохраняется
до подтверждения И карточки, И папки. Ошибки не пропускают строку, cursor не идёт
вперёд. Один script lock защищает обработку формы и повторы от одновременного запуска.

Папка получает стабильный маркер ID проекта; при повторе после потерянного ответа
проверяется существующая папка. Изменение уже подтверждённого folder ID отвергается.
Чек-лист использует optimistic version; операции сохранения и аудит атомарны.
«Выполнено» для кабинетов/событий/CAPI/CRM/запуска требует комментария проверки;
«Не требуется» требует причины. Ответ «Да» в брифе не является проверкой интеграции.

Полный бриф и подготовку видят admin и только назначенный team/buyer. Client и
публичные ссылки не получают бриф. Новые draft можно назначить в «Доступы».
Получить ключ настройки может только admin. Все ответы private/no-store.
Данные брифа не исполняются как инструкции или HTML; внешние URL не скачиваются
автоматически. В журналах Apps Script остаётся только ограниченный код ошибки.

## Проверки и границы подтверждения

Локальные unit/runtime и browser сценарии используют синтетические ответы, не
создают тестовых клиентов в production. Проверены повторная доставка, старые записи,
чужой источник, права, конфликты версий, обязательные проверки, редактирование без
потери оригинала, сохранение дат/ответственных, мобильное окно и установка скрипта.
Отдельно проверяются существующие финансовые UI/права, без изменения их правил.

Состояние публикации и результаты проверок фиксируются в release-документе.
Первый настоящий onFormSubmit/создание папки нужно подтвердить после Google setup.
Не отправлять синтетический бриф в рабочий intake ради проверки.
