# CRM: drag scrolling, pinned stages and immediate moves

Cards dragged from the bottom of a long column can now be dropped into any stage at the same page height. Columns stretch to the full board height while the page remains the vertical scroll container. A sticky strip repeats stage names and counts, follows horizontal board scrolling, and accepts drops. The existing range and arrow navigation remain available on desktop and mobile.

Native dragging uses vertical and horizontal edge autoscroll driven by animation frames, tracking both dragenter and dragover because browsers do not report every pointer move as dragover. Wheel events during a drag scroll the page vertically and the board horizontally. Drop, dragend, Escape, blur, hidden-document and full board replacement stop scrolling.

Ordinary stage moves relocate the existing card immediately and adjust current qualification, sales and revenue metrics using the same explicit stage qualification rule as the server. Pending cards cannot be edited, deleted or dragged twice. Successful writes update the version without another board GET. Sales still open the amount/currency form before changing status. Errors roll back only the affected move, show a sticky error and reconcile with CRM; other pending/saved moves are retained. Board reads wait for pending writes in their own scope, reject stale responses and clone cached data before mutation. Late responses cannot change another project's or board's view. When an older card enters a partially loaded column, subsequent explicit pagination rescans and deduplicates that column so offsets cannot skip leads.

Validation: 203 automated tests passed. Seven focused browser scenarios cover real native drags from the bottom in master and embedded ShadowRoot CRM, pinned header drops, autoscroll in both directions, horizontal edge scrolling, wheel fallback, optimistic movement with delayed responses, concurrent save failure, scope changes, server version conflicts, pagination and mobile page scrolling. Four existing CRM regression scenarios and the multiple-board desktop/mobile scenario also passed (12 browser scenarios total). Desktop/mobile screenshots were inspected locally. Direct browser access to production is blocked by the environment network policy; the real Worker deployment and Pages registry were verified through Cloudflare API. No production CRM test leads, schema changes or provider writes were used.
