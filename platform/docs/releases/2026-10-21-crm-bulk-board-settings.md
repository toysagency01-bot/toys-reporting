# Bulk lead actions and editable kanban boards

CRM has an explicit selection mode with individual card checkboxes, loaded-stage selection, and a control to select all retrieved matches for the current board/search/status, including unloaded cards. The sticky selection toolbar offers move, delete and cancel. Moving supports another board and its actual pipeline; a sale requests a separate value/currency for each affected lead. Deletion requires a confirmation showing the selected count. Snapshots refresh before confirmation, every write uses existing version checks and idempotency keys, requests run sequentially, and successful/failed results are reported separately. Only failed leads remain selected after a partial result; access loss stops the batch. Scope changes reset selection. Advertising/CRM notifications run once after the batch rather than after every card.

The board-title menu now exposes settings to assigned staff/admins. Users can rename a board, add/remove/rename/reorder columns, and set explicit normal/qualified/sale types. Existing primary and custom board IDs remain intact. When removing occupied columns, users choose surviving stages; their leads transfer through the normal lead endpoint first, preserving qualification, audit and CAPI semantics. If any transfer fails, the columns are retained. Sales must use the move form with individual deal amounts. Transfers and the final settings save are separate operations: successful transfers persist if a later step fails, and the form reports that state. Server guards prevent deletion of a still-occupied stage, invalid pipelines, duplicate names and turning an occupied ordinary column into a sale without explicit deal handling.

Migration `0030_crm_board_settings.sql` adds only an override/version table. The settings write transaction claims the expected board version, migrates canonical stage labels, bumps active lead versions and records an audit event. A rename does not replay historical conversion events. New intake and cross-board moves check the destination configuration version inside their write transaction, so an in-flight request cannot populate a removed or renamed stage. Board editing is restricted to existing staff/admin project scope; bulk actions retain the existing lead-edit/delete authorization.
