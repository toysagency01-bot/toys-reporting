# Advertising qualifications use the lead intake cohort

Project/master reporting and creative attribution now assign the first recorded qualification to the lead's receipt date in the configured CRM timezone. A lead received October 10 and qualified October 21 contributes to October 10 qualifications, including attribution to its actual ad/account/provider. Re-entering qualification still counts once. Deleted leads stay excluded. Sales and revenue retain the first sale event date. Summary metadata explicitly describes each metric's date basis, and project/master dashboards show the distinction. The synthetic demo retains its existing full-cohort sales/revenue methodology and has its own explanatory text.

Native milestone aggregation and the configured legacy status-history attribution path use the same receipt basis. Missing receipt dates in legacy attribution return unavailable rather than substituting qualification dates. Native production receipt dates were checked and none of the qualified records had invalid receipt dates. A read-only audit found three TOYS Agency qualifications whose receipt and qualification dates differ; source/history records were not modified.

The immutable qualification timestamp, milestone ID, event history and delivery queue are unchanged. CAPI still sends the actual qualification time. Operational morning reviews continue to count first status events on the day they happened. No past daily-review documents were rewritten or Telegram messages sent.

Only CRM-bearing browser request keys (master summaries, hierarchy/statistics and creative rankings) use the new `crmBasis=received-v1` key so an old qualification-date result is not restored. Advertising snapshots/import schedules, unrelated caches and refresh policy are unchanged. The new key causes a local snapshot read once per affected period, not a forced provider import; subsequent reloads reuse the result.

Validation: 213 automated tests passed. Four new unit/API scenarios cover delayed qualification, stable CAPI payloads/queues, repeat qualification, sale dates/currencies, receipt boundaries and offset timestamps, project timezones, provider/account separation, deleted leads, both attribution paths and matching master/project summaries. Two new browser scenarios verify intake/event-day counts, cached reloads, method text and period controls on desktop/mobile. Five existing cache/render/CRM-write browser scenarios also passed. Screenshots were inspected locally. Direct production browser access is blocked by environment network policy; deployment was verified through Cloudflare API. No production leads, milestones or integrations were mutated.
