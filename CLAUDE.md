# TOYS AGENCY — бриф для Claude Code

Полная передача контекста по проекту. Собран из долгой рабочей переписки с
Денисом (COO TOYS AGENCY, performance-маркетинг агентство, Тбилиси, клиенты —
локальный бизнес в Европе/США/ОАЭ). Денис нетехнический человек: UI/UX и
маркетинг, но весь деплой делает руками сам — через веб-интерфейс GitHub,
редактор Google Apps Script и SFTP. Он не пишет код сам — весь код пишет
Claude, Денис копирует/вставляет/кликает.

Общайся с ним по-русски, прямо и без долгих предисловий. Он импульсивный,
может материться от усталости — это не относится к тебе лично, продолжай
нормально работать. Не любит, когда его посылают по кругу с недоказанными
догадками (см. раздел «Грабли» ниже) — если не уверен в структуре данных,
проси прислать реальные сырые данные (см. приём с gviz JSON ниже), не гадай.
Не создавай кастомный код под одного клиента в общих файлах — см. раздел про
архитектуру ниже, это принципиально важно для него.

## 2. Дашборд отчётности — архитектура

Репозиторий: GitHub, пользователь `toysagency01-bot`, репозиторий
`toys-reporting`. Публикуется через GitHub Pages:
`https://toysagency01-bot.github.io/toys-reporting/<slug-клиента>/`

Структура репозитория:

```
/core/core.js          — общий движок, ОДИН файл на всех клиентов
/master/index.html     — мастер-дашборд (агрегат по всем клиентам)
/<client-slug>/index.html — крошечный конфиг конкретного клиента
/assets/               — логотипы (toys-logo.svg + логотипы клиентов)
```

Принцип данных: Google Sheets = единственный источник правды. GitHub Pages
читает их анонимно через `gviz` (Google Visualization API, JSONP), без
бэкенда и без ключей на клиенте — **за одним осознанным исключением**, см.
раздел про Karlovarska Sul: там на клиенте лежит ограниченный (по домену +
Sheets API) публичный API-ключ для обнаружения списка листов через Sheets
API v4, потому что gviz не умеет отдавать список вкладок. Это отступление от
принципа "без ключей на клиенте", сделано осознанно для одного клиента —
не тиражировать по умолчанию на остальных без явной причины.

`core.js` подключается в `index.html` клиента, который задаёт только
`window.DASH_CONFIG = {...}`.

Каждый `index.html` клиента — минимальный конфиг:

```js
window.DASH_CONFIG = {
  sheetId: '...',           // таблица с рекламными данными (может отсутствовать,
                             // если кабинетов ещё нет — см. раздел "Клиент без кабинетов")
  title: 'Имя клиента',
  locked: true,              // true = обычный клиент (без выбора аккаунта),
                              // false = мастер-дашборд
  showDrafts: false,
  projectSheetId: '...',     // опционально — проектная таблица
  projectTab: '...',         // опционально — если "План работ" называется иначе
  projectPlanTabs: [...],    // опционально — НЕСКОЛЬКО план-вкладок по каналам
                              // (устаревший механизм, см. projectChannels ниже)
  projectChannels: [...],    // опционально — вкладки-каналы (SMM/Meta/Google) вместо
                              // единой "Проект"; см. раздел Karlovarska Sul
  projectApiKey: '...',      // опционально — вместе с projectChannels включает
                              // динамическое обнаружение листов через Sheets API v4
  showQualified: 'ИмяКлиента', // опционально — вкл. карточки квал-лидов (см. Zoho)
  clientLogoUrl: '...'       // опционально — логотип клиента в шапке
};
```

### КРИТИЧЕСКИ ВАЖНЫЙ АРХИТЕКТУРНЫЙ ПРИНЦИП

Единица масштаба — не клиент, а платформа/паттерн. Если фича нужна только
ОДНОМУ клиенту с уникальной структурой данных (например, воронка CRM у
MyPulse с жёстко зашитыми названиями строк) — она НЕ идёт в `core.js`.
Вместо этого:

1. `core.js` получает маленький универсальный "крючок" (feature-detection:
   `if (typeof window.renderWeeklyReportExtra === 'function') ...`).
2. Реальная логика уходит в отдельный файл (`mypulse-funnel.js` и т.п.),
   который подключает вторым `<script>` тегом только нужный клиент в своём
   `index.html`.

Это уже сделано один раз (см. `mypulse-funnel.js`) — паттерн повторять для
любой будущей client-specific фичи. Денис явно требовал эту дисциплину после
того как я один раз её нарушил.

Если же фича универсальна (применима к любому клиенту при тех же условиях,
даже если сработает у одного) — она идёт в `core.js` с опциональным
config-флагом. Пример: `projectPlanTabs`/`projectChannels` — механизм общий
(любой клиент может завести несколько вкладок-каналов), просто пока
используется только у Karlovarska Sul.

## 4. Meta API — как настроен доступ

- Приложение через developers.facebook.com, use case "Measure ad
  performance" — даёт `ads_read` + `business_management` на Standard Access
  без App Review (это заняло много времени понять — Денис сначала пошёл по
  неверному пути App Review).
- Токен — System User через Business Settings → Системные пользователи →
  `toys-reporting-bot` → постоянный, не истекает.
- Ритуал перед любым деплоем токена: проверить
  `curl 'https://graph.facebook.com/v21.0/me/permissions?access_token=TOKEN'`
  — должен быть `ads_read` в granted.
- Хранится в Script Properties Apps Script проекта как `META_TOKEN`.

### Karlovarska Sul — особый случай

Единственный клиент с вкладками-каналами вместо единой "Проект": верхний
уровень навигации — "Показатели" / "SMM" / "Meta" / "Google" (через
`projectChannels`), а не "Показатели" / "Проект". Также был подключён БЕЗ
`sheetId` изначально (кабинетов ещё не было) — вкладка "Проект" должна была
работать сразу, "Показатели" — показывать "данных нет" без ошибки. Отсюда
родилась правка: если `sheetId` не задан, `core.js` пропускает все три
обречённых запроса (GoogleAds/MetaAds/Insights/MetaAdsFormat) МГНОВЕННО, а
не ждёт 12-секундный таймаут на каждый.

Важное отличие от остальной сети клиентов: у Karlovarska Sul список
под-вкладок каждого канала **не фиксированный** — он подтягивается на лету
через Sheets API v4 (нужен `projectApiKey`, публичный, ограниченный по
домену `toysagency01-bot.github.io/*` и по scope `Google Sheets API`).
Берутся только листы, чьё имя оканчивается на ` (SMM)` / ` (Meta)` /
` (Google)` — так новые листы (клиент активно плодит контентные листы вроде
"Контент-план (SMM)", "Лента сентябрь (SMM)") появляются на сайте
автоматически, без правки кода. Соответствие "базового" имени листа и
режима рендера — таблица `CHANNEL_TAB_MODES` в `core.js` (План работы →
трекер задач, Еженедельная/Месячная сводка → weekly-report, Анализ
конкурентов → competitors, Креативный бриф → creative-brief, всё
остальное — обычная таблица). У этого клиента стандартный список вкладок
из раздела 6 ниже НЕ действует буквально — там сейчас реальные листы вроде
"Ключевые слова", "Объявления", плюс россыпь SMM-контентных листов, а
"ОС по лидам"/"Анализ конкурентов"/"Стратегия"/"Креативный бриф" пока
существуют только как ОДИН общий (не по каналам) лист без приписки.

Также у этого клиента: обычные ("generic", без спецрежима) вкладки проекта
запрашиваются с `headers=0` и сами ищут свою строку-шапку в `renderGeneric`
(а не полагаются на автоопределение Google) — потому что часть реальных
листов имеет нестандартную раскладку (пустая первая колонка, шапка не в
первой строке), на чём автоопределение Google молча ломается и отдаёт
пустые заголовки. Остальные режимы (weekly-report/competitors/
creative-brief/plan) продолжают полагаться на автоопределение Google как и
раньше — их это не касалось.

Пробовали встраивать живую Google-таблицу через iframe вместо своего рендера
(чтобы получить нативные комментарии/редактирование прямо в дашборде) — не
взлетело: Google блокирует интерактивные комментарии/редактирование внутри
чужого iframe. Тестовая страница `karlovarska-sul-k4rm/embed-test.html`
осталась в репозитории как артефакт этого эксперимента, никуда не подключена
— можно удалить, если не нужна как референс.

Полноценная запись заметок/комментариев с сайта обратно в таблицу (через
Google Apps Script Web App) обсуждалась, но пока сознательно отложена —
ничего в эту сторону не менять, пока Денис явно не попросит.

## 6. Стандартные названия вкладок (СТРОГО)

Проектная таблица (одна на клиента): `План работ`, `ОС по лидам`,
`Еженедельная сводка`, `Месячная сводка`, `Анализ конкурентов`, `Стратегия`,
`Креативный бриф`.

Таблица с рекламными данными (одна на клиента): `GoogleAds`, `MetaAds`,
`Insights`.

Общие/служебные: `QualifiedLeads` (в мастер-таблице), `MetaAdsFormat` (в
таблице каждого клиента).

Это правило — для клиентов на "классической" единой вкладке "Проект"
(`initProject`/`EXTRA_TABS`/`PLAN_TABS` в `core.js`). У Karlovarska Sul
(единственного на `projectChannels` + динамическом обнаружении) список
листов вместо этого читается из реальной таблицы — см. раздел про неё выше.

ПРАВИЛО: названия должны совпадать дословно. Если лист не найден, Google's
gviz молча подставляет первую попавшуюся вкладку вместо ошибки — это ловили
минимум 4 раза за проект, самый частый источник багов. При переименовании —
всегда удалять старое название ПОЛНОСТЬЮ и печатать заново с нуля (скрытые
непечатаемые символы после копипаста не видны глазом, но ломают точное
сравнение строк).

## 7. Возможности `core.js` (полный список на сегодня)

- Карточки "Квал-лидов"/"Цена квала" (см. Zoho, опционально).

## 8. Логика подсчёта конверсий (Meta) — важные баги, уже исправленные

Файл `meta_to_sheets.js` (общий скрипт `dailyMeta`, один на всех
Meta-клиентов). Ключевые уроки, НЕ повторять:

1. `lead`, `onsite_conversion.lead_grouped`, `offsite_conversion.fb_pixel_lead`
   — это НЕ независимые метрики, а частично дублирующие друг друга
   представления одного и того же события. Раньше суммировались все —
   получался 2-3-кратный переучёт. Исправлено: берётся ОДНА метрика по
   приоритету (`lead_grouped` > `lead` > `fb_pixel_lead`), не сумма.
2. `offsite_conversion.fb_pixel_custom` может быть вообще не связан с
   лидами — на реальных данных видели значение 239 у кампании с 42
   реальными лидами. Теперь используется только как последний резерв, когда
   вообще никакого другого сигнала о конверсиях нет.
3. Кастомные конверсии пикселя проверяются по ОБОИМ префиксам —
   `offsite_conversion.custom.*` И `onsite_conversion.custom.*` (раньше
   проверялся только offsite, onsite молча терялся).
4. Никогда не угадывай `action_type` по документации — только по реальному
   `curl` дампу конкретного кабинета
   (`https://graph.facebook.com/v21.0/act_<ID>/insights?level=campaign&fields=campaign_name,actions&date_preset=last_30d&access_token=TOKEN`).

## 9. Формат креативов (видео/статика/карусель)

Нет одного надёжного enum-поля у Meta — определяется ЭВРИСТИКОЙ по
структуре объекта creative (`video_id` → видео, несколько
`child_attachments` → карусель, наличие картинки → статика). Это может
ошибаться на нестандартных типах кампаний — при первом запуске у нового
клиента стоит сверить колонку `format` в листе `MetaAdsFormat` глазами, не
появилось ли много "Другое" не по делу.

## 10. Grep-паттерн отладки, который решает 90% проблем

Когда что-то "не грузится" или "показывает не то":

1. Не гадать по документации Meta/Google/Zoho — просить у Дениса ссылку на
   прямой gviz JSON-дамп конкретной вкладки:
   ```
   https://docs.google.com/spreadsheets/d/<ID>/gviz/tq?tqx=out:json&sheet=<URL-encoded-имя>
   ```
   Открывается в браузере, скачивается `json.txt`, Денис копирует
   содержимое в чат.
2. Смотреть на `parsedNumHeaders` в ответе — если > 1, Google утащил часть
   верхних строк в `cols[].label` вместо `rows[]` — частый источник "почему
   не находит данные".
3. Если пришли не те данные (структура другой вкладки) — это тот самый баг
   с подстановкой первого листа при неверном имени.

## 11. Zoho CRM интеграция (квал-лиды) — MyPulse

Файл `zoho_qualified.js`, живёт в Apps Script проекте мастер-таблицы (не
таблицы клиента — важно, лист `QualifiedLeads` общий на всех).

Архитектура:

- OAuth через Self Client (не обычный веб-флоу) — `ZOHO_CLIENT_ID`,
  `ZOHO_CLIENT_SECRET`, `ZOHO_REFRESH_TOKEN` в Script Properties.
- Порядок этапов воронки скрипт узнаёт САМ через API
  (`/crm/v2/settings/fields?module=Deals`) — никогда не проси человека
  вручную перечислять этапы, это лишнее и хрупкое.
- Лид считается квалом, если текущий этап — целевой (`Demo session booked`
  у MyPulse) ИЛИ любой более поздний по порядку воронки.
- Дедупликация через список уже посчитанных ID (лист `QualifiedLeadsIds`),
  не через дату — иначе один и тот же лид считается заново при каждом
  касании сделки дальше по воронке.
- Ad-attribution фильтр: считается квалом только если
  `Lead_Source === 'Meta Ads'` ИЛИ `UTM Source` (API-имя поля узнаётся
  динамически по подписи "UTM Source" через settings/fields) равен `fb`/`ig`
  — `organic` и прочее не считается. Это добавлено по прямому требованию
  Дениса, ключевая деталь, не убирать.
- Одна функция `syncQualifiedLeads()` — и для бэкафилла (первый запуск на
  пустой истории), и для ежедневного дозаписывания. Не изобретай отдельную
  "разовую" функцию, она не нужна благодаря ID-дедупликации.
- Известный технический долг: `getCountedIds()` читает ВЕСЬ лист
  `QualifiedLeadsIds` на каждый запуск — при подключении нескольких клиентов
  на Zoho когда-нибудь стоит разбить на отдельные листы
  `QualifiedLeadsIds_<клиент>` для производительности. Пока клиент один
  (MyPulse) — не критично, но не забыть при масштабировании.
- Домен Zoho — `.com` (не `.eu`/`.in`).

Если появится второй клиент на Zoho — переиспользовать этот же скрипт,
менять только `ZOHO_CLIENT_KEY`/токены/этап под него. Если появится клиент
на ДРУГОЙ CRM (Pipedrive/amoCRM) — это отдельный скрипт под платформу, не
подмешивать в `zoho_qualified.js`.

Если у CRM нет рабочего API или разработка не окупается — универсальный
fallback: специалист руками вписывает число в тот же формат листа
`QualifiedLeads` (2 колонки, 10 секунд работы) — работает для любой CRM без
всякой интеграции.

## 12. WordPress-сайт toys-agency.com

Тема `toys` (папка `wp-content/themes/toys/`), кастомная, без
билд-системы (весь CSS пишется инлайн в `<style>` внутри PHP-шаблонов
страниц).

Формы лидов:

- Главная страница — трёхшаговый квиз
  (`template-parts/section-multistep-form.php`), AJAX action
  `submit_multistep_form`, обработчик `handle_multistep_form_submission` в
  `functions.php`.
- Футер (`footer.php`) — простая форма, action `submit_footer_form`,
  обработчик `handle_footer_form_submission`.
- Обе шлют `wp_mail()` на адрес из ACF-поля `recipient_email` (Options
  Page), фолбэк — email администратора WP.
- Известная проблема и решение: письма падали в спам (GoDaddy + голый PHP
  `mail()` без SPF/DKIM). Решение — плагин WP Mail SMTP (бесплатный) +
  отправка через Gmail (бесплатно, лимит ~500/день).

Самостоятельные лендинги (без шапки/футера темы — свой `<html>` с
`wp_head()`/`wp_footer()`, без `get_header()`/`get_footer()`):

- `page-avtoservis.php` — лендинг для автосервисов. Полностью переработан
  (см. историю правок — блоки Hero/Проблемы/Решение/Тест-драйв/
  Кейсы/КакМыРаботаем/Сработаемся/Таймлайн/ФинальныйCTA), включает
  CSS-анимацию болида F1 (SVG) и реалистичные спидометры (детализированный
  SVG с градиентами, не векторная плоская иконка) в блоке "Как мы
  работаем". Использует свою систему CSS-токенов (`--ta-bg:#0a0c0e`,
  `--ta-teal:#25ddcc`, `--ta-bg2:#111417`, `--ta-line:#23282d`,
  `--ta-muted:#aab2b8`), класс-неймспейс `.ta-auto`.
- `page-local-business.php` — новый лендинг под локальный бизнес за
  рубежом (в разработке, блоки добавляются по одному от Дениса).
  Использует свой неймспейс `.lb`, переиспользует ТУ ЖЕ форму
  (`get_template_part('template-parts/section-multistep-form')`), не
  дублирует её.

Стиль сайта (главная + `/service/`): тёмный фон, крупный жирный заголовок
прижат влево (НЕ по центру), monospace-эйбрау (`// текст`) бирюзового цвета
над заголовками, простые пилюли-ссылки для списков категорий (не карточки с
рамками) — свериться с живыми страницами перед новыми блоками, не
изобретать оформление от себя.

## 13. Процедура: добавить нового клиента (Meta-only, самый частый случай)

1. Business Settings → Системные пользователи → `toys-reporting-bot` → Add
   Assets → выбрать кабинет → View performance.
2. TOYS Config → новая строка: имя (B), `meta_account_id` (G). Если нужен
   конкретный slug — вписать в C ДО следующего шага.
3. Apps Script (проект с `dailyMeta`) → функция setupMeta → Выполнить. В
   логе: `[new] Имя -> ссылка`.
4. Скопировать новую строку из TOYS Config целиком.
5. Собрать `index.html` (см. шаблон в разделе 2).
6. Разово прогнать dailyMeta вручную — проверить `[ok] Имя: строк N`.
7. Залить папку на GitHub.
8. Проверить доступ на таблице клиента: "Все, у кого есть ссылка →
   Читатель".
9. Если есть проектная таблица — сверить названия вкладок со стандартом
   (раздел 6), при расхождении переименовать (удалить полностью —
   напечатать заново).
10. Проверить на живой ссылке.

Если кабинета ещё нет, а проектная таблица уже есть — можно собрать
страницу сразу без `sheetId` (пункты 1-3, 6 пропускаются). "Проект" будет
работать сразу, "Показатели" покажут "данных нет" до появления `sheetId`.

## 14. Как работать с Денисом — стиль

- Прямая, техническая речь, без длинных предисловий и без извинений сверх
  меры. Если ошибся — коротко признать и сразу чинить.
- Никогда не отдавать частичный/фрагментарный код — только полный файл
  целиком, готовый к вставке.
- Не делать unsolicited дизайнерских или контентных решений сверх того, что
  прямо попросили.
- Если не уверен в структуре данных — просить реальный дамп (раздел 10), не
  гадать и не отправлять "на деревню" повторными догадками.
- Если правка задевает нескольких клиентов — явно предупреждать об этом
  заранее, а не постфактум.
- Денис ценит честные оценки рисков (в т.ч. рыночных) без приукрашивания.
